# Earshot on Fire TV

The primary track. A React Native TV app that runs the hearing screen on
a remote control, and does the half a browser cannot: watching how far
past a programme a household is listening.

## Run it on a device

```
adb connect <your Fire TV ip>:5555
adb install earshot-tv-v0.1.0.apk
```

The APK contains `arm64-v8a`, `armeabi-v7a` and `x86_64`, so it installs
on Fire TV hardware as well as an emulator. Do not narrow that to
`x86_64` to speed up emulator builds: Fire TV devices are ARM, and an
x86-only build fails on every real one with
`INSTALL_FAILED_NO_MATCHING_ABIS` while working perfectly in testing.

## Build it

Two steps, in this order, from two different paths. That is not a
preference, it is the only combination that works on Windows, and both
halves are in `FRICTION_LOG.md`.

```
npm run bundle          # from the real path, e.g. C:\...\earshot\tv
```

```
subst X: <repo>                               # once per session
set JAVA_HOME=C:\Program Files\Java\jdk-17
cd X:\tv\android
gradlew assembleRelease
```

### Before the first build

Two things that are not in the repository and have to exist on the
machine, because both are machine-specific and both must stay out of
version control.

**`android/local.properties`**, naming the Android SDK:

```
sdk.dir=C:\\Users\\you\\AppData\\Local\\Android\\Sdk
```

Without it Gradle stops with "SDK location not found", which is clear
enough, except that it arrives after the whole plugin graph has
configured and reads like a project defect rather than a missing local
file.

**`JAVA_HOME`**, pointing at JDK 17 or later. Gradle 9 requires it and
otherwise takes whatever `java` is first on the path, which on a machine
with an old JRE installed is Java 8. Installing Android Studio is not
sufficient if something older is also present.

### Why the build is split across two paths

The native build cannot run from the real repository path, because it is
long enough to trip the 260-character `MAX_PATH` limit in CMake. So
Gradle runs from a `subst` drive.

Metro cannot run from the `subst` drive, because Node resolves `X:` back
to `C:` and the two disagree about file identity. So the JavaScript
bundle is generated by hand from the real path, which is why
`android/app/build.gradle` lists `release` in `debuggableVariants`: that
makes the React Native plugin skip its own bundling step.

**The cost of that split, recorded because it bit a sibling project.**
No Gradle task regenerates `index.android.bundle`, and the file is not
tracked, so a stale bundle is invisible: `assembleRelease` succeeds and
ships whatever JavaScript was last produced by hand. Run `npm run
bundle` before every release build, and check the bundle inside the APK
against the one on disk rather than trusting the timestamps.

The same root cause bites native modules that run codegen. Anything with
a `generateCodegenSchemaFromJavaScript` task will fail with "this and
base files have different roots". The app therefore carries only the
native dependencies it actually uses.

## What is sample data, and what is not

The viewing history on the home screen is sample data and the screen
says so. A household has to watch for months before this product has
anything to say, which is correct behaviour and a poor demonstration.

The check itself is real, and so is the audio: eight digits synthesised
with Amazon Polly, levelled to within 0 dB of each other, against noise
shaped to their own spectrum.

## The one thing this app cannot do

Fire TV ships Dialogue Boost, and there is no developer API to read
whether it is on, no documented intent to open its settings screen, and
no way to request it on a customer's behalf. The app explains where the
setting lives and cannot confirm anybody found it. `FRICTION_LOG.md`
entry 1.
